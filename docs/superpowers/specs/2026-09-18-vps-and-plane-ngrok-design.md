# VPS deployment and Plane ngrok tunnel design

## Goal

Deploy the current SmartQoldau production stack to the supplied Contabo VPS and expose the locally running Plane instance on port 8090 through an automatically assigned ngrok HTTPS endpoint.

## Scope and boundaries

Two deployment units are intentionally independent:

1. **SmartQoldau VPS stack.** The application runs on the VPS in Docker Compose, with PostgreSQL, Redis, and MinIO reachable only through the Compose internal network. Its runtime configuration and generated secrets remain only on the server.
2. **Local Plane tunnel.** ngrok runs on the current local machine and forwards its temporary public HTTPS hostname to `http://127.0.0.1:8090`. This does not move Plane to the VPS.

The ngrok free hostname is generated by ngrok and may change after a tunnel restart. A paid/reserved ngrok domain or a DNS name is outside the current scope.

## SmartQoldau architecture

The server receives a copy of the repository under `/opt/smart-qoldau`, excluding local environment files, Git metadata, generated dependencies, and any credentials. Deployment uses the repository's `infra/docker-compose.prod.yml`. Docker named volumes retain PostgreSQL, Redis, and MinIO data across container restarts.

Production variables are created in `/opt/smart-qoldau/infra/.env` with restrictive permissions. The deployment must set the documented database, JWT, cookie, S3, LiveKit, public API, and bootstrap-admin values. The bootstrap password is removed after an administrator can authenticate.

No public DNS hostname was supplied. The existing Caddy configuration expects three DNS hostnames and automatic TLS, so it is not enabled in this initial IP-only deployment. The stack is first validated from the VPS network and then, if required, an explicitly scoped temporary HTTP proxy can be added for external smoke testing. Public HTTPS, browser-accessible API origins, and LiveKit/TURN production access require a real DNS domain and are deferred.

## Plane tunnel lifecycle

The local ngrok client reads the existing local credential without copying it into the repository or the VPS. It starts `ngrok http 8090`, obtains the assigned HTTPS URL from the local ngrok API/process output, and is installed as a local user systemd service so it restarts after a local reboot. The service binds Plane only through the localhost target; it does not expose port 8090 directly on the network.

## Error handling and validation

Before changing the server, validate SSH authentication and record the server OS, Docker availability, free disk capacity, and firewall state. Abort before a destructive action if the server has an incompatible operating system, insufficient disk, an occupied deployment path, or missing required production configuration.

After deployment, validate Compose service health, migration completion, local backend health, and persistent-volume declarations. After the Plane tunnel starts, validate that it has a public HTTPS URL and that its local target returns an HTTP response. Do not print passwords, ngrok tokens, or generated secrets in logs or chat.

## Rollback

Application rollback is performed by stopping the Compose stack and restoring the prior release directory/image tags. Docker volumes are never deleted as part of deploy or rollback. The Plane rollback is `systemctl --user disable --now plane-ngrok.service`, which stops only the tunnel and leaves Plane unchanged.
