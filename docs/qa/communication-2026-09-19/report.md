# Проверка связи клиент ↔ специалист, 19 сентября 2026

Проверка выполнялась на отдельном локальном стенде из текущих исходников. Два независимых Chromium, настоящие Nest API, PostgreSQL, Redis, Socket.IO, LiveKit и WebRTC. Камеры и микрофоны синтетические: видеопоток Chromium и разные звуковые сигналы 440/660 Гц. Реальные аккаунты, платежи и пользовательские данные не использовались.

## Подтверждённые сценарии

- Чат: сообщения в обе стороны, отсутствие дублей, история после перезагрузки обоих участников.
- Аудио: входящие RTP-пакеты и ненулевая энергия звука у обоих участников; камера не включается.
- Видео: входящие кадры декодируются у обоих участников, элементы видео получают изображение.
- Микрофон: выключение/включение меняет состояние реальных локальных дорожек.
- Повторное подключение: после выхода клиента специалист теряет удалённую дорожку; после повторного входа связь восстанавливается в обе стороны.

## Исправления

1. Запрос допуска к звонку теперь использует механизм обновления пользовательской сессии.
2. Ошибки допуска разбираются по фактическому вложенному контракту API, чтобы показывать правильную причину отказа.
3. Обе страницы следят за изменением статуса консультации через WebSocket, сверяют его по API и обновляют интерфейс; резервная проверка каждые 15 секунд восстанавливает пропущенные события. После завершения клиентский чат становится только для чтения и медиадорожки обоих участников останавливаются.

## Границы проверки

Это проверка локального транспорта с синтетическими устройствами. Физические камеры/микрофоны, Safari/Firefox, мобильные браузеры, интернет-сети и TURN через NAT требуют отдельного прогона. Не является подтверждением готовности production-инфраструктуры.

Backend проверяет статус консультации при выдаче нового media-token. Уже выданный LiveKit JWT имеет срок жизни 2 часа; принудительное аннулирование ранее выданного допуска после завершения консультации не реализовано. Остановка штатных веб-клиентов и запрет нового допуска не равнозначны серверному отзыву старого JWT.

## Артефакты и повторный запуск

- `evidence/results.json`: проверяемые шаги и статистика приёма RTP.
- `evidence/*-client.png`, `evidence/*-expert.png`: страницы обоих участников.
- `backend/scripts/seed-comm-fixtures.cjs`: защищённый генератор данных только для базы smartqoldau_comm_test на localhost:15439.
- `web/scripts/test-communications.cjs`: настоящий двусторонний браузерный прогон без подмены API или транспорта.

Браузерный скрипт требует COMMUNICATION_FIXTURES (секретный JSON от seed), COMMUNICATION_ARTIFACTS (каталог отчёта), COMMUNICATION_TONES (client.wav и expert.wav), опционально COMMUNICATION_BASE_URL (по умолчанию http://127.0.0.1:3310). Секретные fixture/env файлы хранятся вне репозитория.

## Финальный результат

**3/3 двусторонних браузерных сценария PASS.** Во всех трёх форматах эксперт завершил консультацию через интерфейс; API подтвердил COMPLETED/CAPTURED (платёжный провайдер mock). Клиент автоматически перешёл в режим чтения; в аудио/видео живых отправляющих дорожек не осталось у обоих участников. Камера после выключения/включения снова передавала новые кадры.

Посторонний пользователь получил 404 на историю и media-token. После завершения оба участника получили 409 на новый media-token, а реальные Socket.IO chat.send отклонены с CONSULTATION_NOT_ACTIVE.

Финальная сборка web успешна. Unit:654/654,95 наборов; fixture safety:5/5. До исправления завершения все 3 браузерных сценария воспроизводили активную кнопку отправки у клиента после завершения экспертом.

Временные процессы и пять контейнеров тестового стенда остановлены и удалены после проверки. Основной стенд не изменялся; правки исходников не развёрнуты в production.
