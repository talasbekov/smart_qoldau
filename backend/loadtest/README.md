# Нагрузочный сценарий (эпик E11)

Критерий из мастер-плана: **200 одновременных консультаций и 500
онлайн-экспертов**. Здесь лежит сценарий, который эту нагрузку
воспроизводит, и метрики, по которым его читают.

Это не e2e-спек. E2e (448 штук) отвечают на вопрос «правильно ли
работает логика», нагрузочный — «что происходит с живым процессом, когда
в него одновременно приходят сотни пользователей». Поэтому он ходит по
HTTP и WebSocket к **запущенному серверу**, а не поднимает приложение
внутри Jest.

## Как запускать

```bash
# 1. Инфраструктура и база (обычная dev-база, не тестовая)
docker compose -f ../infra/docker-compose.dev.yml up -d postgres redis minio
npx prisma migrate deploy
npx ts-node prisma/seed.ts            # справочник тем

# 2. Сервер в боевом режиме — мерить dev-watch бессмысленно
npm run build
NODE_ENV=production node dist/main.js

# 3. Нагрузка (в другом терминале)
npm run loadtest
```

Сценарий читает `backend/.env` (через `dotenv/config`): ему нужны те же
`DATABASE_URL` и `JWT_SECRET`, что у сервера, — токены он подписывает сам.

### Параметры

| Переменная | По умолчанию | Что делает |
| --- | --- | --- |
| `LOADTEST_EXPERTS` | 500 | сколько экспертов выходит онлайн |
| `LOADTEST_CONSULTATIONS` | 200 | сколько консультаций идёт одновременно |
| `LOADTEST_CHAT_MESSAGES` | 4 | сообщений в каждой консультации |
| `LOADTEST_BASE_URL` | `http://localhost:3000/v1` | цель HTTP |
| `LOADTEST_WS_URL` | `http://localhost:3000/ws` | цель WebSocket |
| `LOADTEST_PREPARE_POOL` | 50 | параллельность подготовительных запросов |
| `LOADTEST_EVENT_TIMEOUT` | 120000 | сколько ждать события сокета, мс |
| `LOADTEST_KEEP` | — | `true` — не убирать данные после прогона |

Уменьшенный прогон для проверки самого сценария:

```bash
LOADTEST_EXPERTS=10 LOADTEST_CONSULTATIONS=3 npm run loadtest
```

## Что происходит внутри

**Подготовка.** Эксперты и клиенты создаются напрямую через Prisma,
токены подписываются секретом сервера. Гонять 700 SMS-логинов ради выхода
на старт бессмысленно: bcrypt на кодах занял бы больше времени, чем сам
замер, и мерил бы не то. Телефоны — с префиксом `+7799`, уборка ходит по
нему же, поэтому прогон не задевает никаких других данных.

**Фаза A — 500 экспертов онлайн.** Каждый ставит расписание 24/7,
переходит в `ACCEPTING` и открывает WebSocket, как настоящее приложение.
Сокеты открываются все сразу, без пула: одновременно висящие соединения —
это и есть проверяемое свойство. В конце фазы `GET /matching/online-count`
показывает, скольких из них сервер действительно считает доступными.

**Фаза B — 200 консультаций.** Клиенты одновременно создают заявки.
Матчинг сам решает, кому уйдёт оффер, — эксперт принимает его по событию
`offer.new`, клиент узнаёт о матче событием `request.updated` с
`consultationId`. Дальше стороны обмениваются сообщениями (замеряется
полный круг «клиент отправил → сервер зашифровал, сохранил, разослал →
эксперт получил»), после чего эксперт закрывает консультацию с исходом.

## Как читать результат

Таблица метрик печатается в консоль и дублируется в Markdown — её
вставляют в отчёт. По каждому шагу: сколько прошло, сколько сорвалось и
p50/p95/p99/max.

Смотреть нужно на **хвосты**, а не на среднее и не на p50: нагрузочный
тест затевается ровно ради тех запросов, которые попали в 5 % худших.
Ненулевой столбец «Ошибок» — всегда повод разобраться: сценарий не
считает штатным ни один сорванный шаг.
